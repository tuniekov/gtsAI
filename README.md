# gtsAI

Шлюз ИИ для gtsERP: чат, который читает данные системы, предлагает правки и
применяет их с подтверждением и откатом.

Подробности устройства — в [CLAUDE.md](CLAUDE.md).

## Где открывается

| Место | Что это |
|---|---|
| Сайт → Администратор → **Чат ИИ** | рабочая страница, ставится пакетом на оба сайта (`_build/configs/resources.js`) |
| Менеджер MODX → Компоненты → **ИИ (gtsAI)** | подключения, настройки чатов, история и лог вызовов |
| Страница расчёта → левое меню → **Чат ИИ** | чат с контекстом открытого расчёта |

## Подключение к провайдеру

Подключение `gtsAI` (протокол Anthropic, `https://gtsai.ru`) пакет везёт с собой
и на пустой установке создаёт первым — чаты ссылаются на него через `conn_id = 1`.
**Ключа в пакете нет и быть не может:** строки данных находятся по имени и
перезаписываются при каждой установке, так что пустой ключ в пакете стирал бы
вписанный на площадке.

Ключ вписывают один раз: **Компоненты → ИИ (gtsAI) → Подключения**. Пока он
пуст, чат так и отвечает — куда идти, вместо запроса к провайдеру впустую.

⚠️ **Если на площадке стоит старое подключение `neiro-api`** (адрес
`https://neiro-api.ru`), переименуйте его до установки: имя `gtsAI`, адрес
`https://gtsai.ru`. Тогда пакет найдёт строку по имени и обновит на месте,
а ключ сохранится. Иначе рядом появится второе подключение — пустое, без ключа.
Старый адрес продолжает работать, так что спешки нет.

## Какие чаты везёт пакет

| Чат | Откуда приезжает | Что умеет |
|---|---|---|
| `default` | gtsAI, одинаков везде | чтение таблиц; ничего не знает про конкретную систему — пакет ставится и туда, где gtsERP нет |
| `admin` | gtsAI, **свой текст на каждом сайте** (`_build/configs/data.js`, блоки `modx28` и `vk24`) | чтение + SQL; в промпте перечислены таблицы этой площадки |
| `raschet` | **gsRaschet**, а не gtsAI | правка строк расчёта с подтверждением; группы `Administrator,itr,manager` — как у самих расчётов |

⚠️ Строки находятся по `name` и перезаписываются при каждой установке пакета.
Правку промпта вносить в `data.js` того пакета, который этот чат везёт, а не
в админке — иначе она исчезнет на следующей установке.

## Доступ к базе только на чтение

Чат умеет отвечать на вопросы, которых не достать через таблицы, — сводные
цифры, группировки. Для этого есть инструмент `sql_query`, и он ходит в базу
**отдельным пользователем MySQL, у которого есть только SELECT**.

Почему именно так, а не фильтром по словам в запросе: фильтр обходится —
точкой с запятой, комментарием, `SELECT … INTO OUTFILE`. Права пользователя
обойти нельзя. Проверки в коде (один запрос, только SELECT/SHOW/EXPLAIN,
обязательный LIMIT, чёрный список таблиц) эту защиту дополняют, а не заменяют.

### Что сделать: запустить один скрипт

Скрипт [`_install/sql_readonly.sql`](_install/sql_readonly.sql). Сверху в нём три
строки — имя базы, префикс таблиц и пароль, который вы придумываете. Всё три
берутся из `core/config/config.inc.php` вашего сайта (`$database_name`,
`$table_prefix`), кроме пароля.

```sql
SET @db     = 'modx28';                -- $database_name
SET @prefix = 'modx_';                 -- $table_prefix
SET @pass   = 'ПРИДУМАЙТЕ_ПАРОЛЬ';     -- пароль нового пользователя
```

Запустить от администратора MySQL:

```bash
mysql -u root -p < _install/sql_readonly.sql
```

или вставить целиком в phpMyAdmin → вкладка **SQL**.

Скрипт сам заведёт пользователя `gtsai_ro`, выдаст ему **только SELECT и только
на вашу базу**, ограничит 200 запросами в час и пропишет логин с паролем в
системные настройки MODX. В конце он печатает права — ожидаются ровно две
строки: `USAGE ON *.*` и `SELECT` на вашу базу.

Больше ничего не нужно: ни вписывать адрес базы, ни чистить кэш. Адрес чат берёт
тот же, которым ходит сам сайт, а настройки читает напрямую из таблицы.

Пользователь заводится на два адреса — `'%'` и `'localhost'`. Какой из них
сработает, зависит от того, идёт сайт к базе по сети или через сокет; делаем оба,
чтобы не разбираться. (Именно здесь легко споткнуться: на OSPanel база доступна
по имени модуля, `mysql:host=mysql-5.7`, и `'gtsai_ro'@'localhost'` ей не подходит.)

### Если база на другом сервере

Тогда и только тогда заполните настройку `gtsai_sql_dsn` — строку подключения
PDO, например `mysql:host=10.0.0.5;dbname=modx28;charset=utf8mb4`. Пока она
пуста, используется подключение самого сайта, и это нужный случай почти всегда.

| Настройка | Что в ней |
|---|---|
| `gtsai_sql_user`, `gtsai_sql_password` | заполняет скрипт |
| `gtsai_sql_dsn` | пусто = база сайта; заполнять только для другого сервера |
| `gtsai_sql_deny` | таблицы, невидимые даже на чтение (по умолчанию `modx_users,modx_user_attributes,gtsapi_tokens`) |

Пока у пользователя нет логина и пароля, инструмент SQL модели не выдаётся
вовсе — даже если он включён в настройке чата.

Пароль переживает сборку пакета: в `_build/config.js` стоит
`update.settings: false`. Менять на `true` нельзя — установка вернёт всем
настройкам значения из конфига, то есть сотрёт пароль.

### 3. Включить в нужном чате

В менеджере: **Компоненты → ИИ (gtsAI) → Настройки чатов** → у нужной записи
поставить «Доступ к SQL (только чтение)».

### Что проверено

| Запрос из чата | Чем кончается |
|---|---|
| `SELECT …` | выполняется; без `LIMIT` дописывается свой (по умолчанию 50, максимум 200) |
| `SELECT 1; DROP TABLE …` | «Только один запрос без точки с запятой» |
| `UPDATE …`, `DELETE …`, `CREATE …` | отбивает проверка, а под ней — база: `1142 command denied` |
| `SELECT … FROM modx_users` | «К таблице modx_users обращаться нельзя» (список `gtsai_sql_deny`) |
| `SELECT … INTO OUTFILE` | «запрещённая конструкция»; `LOAD_FILE()` вернул бы NULL — права FILE нет |
| `SHOW TABLES`, `DESCRIBE` | выполняются (им `LIMIT` не дописывается — они его не принимают) |

⚠️ У инструментов таблиц права пользователя работают, у SQL — нет: запрос
видит всё, что видит пользователь базы. Поэтому включать его стоит там, где
чат и так для администраторов, а чувствительные таблицы держать в `gtsai_sql_deny`.
